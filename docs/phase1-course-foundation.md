### What the research shows

**Topics common across every credible source:** AWR/ADDM/ASH, the Oracle time model (DB Time, CPU time, wait time), wait event interpretation, execution plan reading via `DBMS_XPLAN`, optimizer statistics and cardinality estimation, memory (SGA/PGA) management, and basic I/O analysis. Any 30-day course that omits these is not a credible Oracle performance course — they anchor Stages 1–8 of this design.

**Topics Oracle expects a working DBA to understand** (per the official Performance Tuning Guide and the 1Z0-084 blueprint) but that generic marketplace courses routinely under-teach: the distinction between foreground and background wait events, AWR Compare Periods reports for before/after validation, SQL Plan Management (baselines) for plan stability, and Resource Manager as a concurrency lever. These are folded into Stages 3, 4, 8, and 9.

**Topics commonly missing even from Oracle's own official material:** a repeatable *investigation methodology* that starts from "what is slow" rather than "here is a feature"; explicit treatment of false leads and victim-vs-root-cause reasoning during an incident; OS-level correlation as a first-class step rather than an afterthought; and clear guidance on when *not* to add an index, change a parameter, or grow SGA. These gaps are exactly what the Measure→Observe→Hypothesize→Prove→Change→Validate philosophy (below) and the mandatory "false leads" field in every scenario are designed to close.

**Heavily theoretical topics across the market:** optimizer internals, memory architecture diagrams, wait-event taxonomies. These are real prerequisites but are compressed to the minimum needed before every one of them is immediately anchored to a live, reproducible demo (per the lab design in this document) — theory is capped at roughly 20–25 minutes per day specifically to prevent this course from drifting into documentation-recitation.

**Highly practical, high-leverage topics that distinguish an experienced performance engineer from an average DBA** (identified from the Tanel Poder / OraPub material and folded into Stages 4, 9, 12, 13, 14): reading ASH like a story instead of a table; correlating a wait event with the exact blocking session/object/plan line responsible for it; distinguishing "the wait event is the symptom, not the cause" in concurrency and I/O problems; recognizing when cardinality misestimation — not a missing index — is the real defect; and validating a fix quantitatively rather than declaring victory because "it feels faster."

**Real-world troubleshooting patterns adopted directly into the course structure:** starting from symptom and working backward to evidence (never starting from a feature and looking for a demo to justify it); explicitly documenting false leads in every scenario, because production incidents are rarely solved on the first hypothesis; separating victims (sessions waiting) from root causes (the session/SQL/resource actually consuming or blocking); and closing every investigation with a quantified before/after comparison.

## Deliverable 2 — Curriculum Design Philosophy

### Target audience
Working Oracle DBAs and database professionals who already know basic administration and SQL (can write joins, understand what an index is, have run `EXPLAIN PLAN` at least once) but have never systematically investigated a production performance incident from symptom to proven root cause. Not aimed at absolute SQL/DBA beginners, and not aimed at people who already run 40-hour advanced troubleshooting seminars — it is the bridge between those two.

### Prerequisites
Working knowledge of SQL (joins, aggregation, subqueries), basic Oracle architecture (instance vs. database, background processes at a naming level), comfort in SQL*Plus/SQLcl, and `CREATE`/`SELECT`/`DML` privileges in a personal or shared non-production Oracle 19c environment. No prior AWR/ASH/wait-event experience is assumed — Days 1–8 build that from zero.

### Teaching philosophy
Every day, every lab, and every scenario in this course enforces one loop:

**Measure → Observe → Hypothesize → Prove → Change → Validate**

Concretely this decomposes into the chain the student must learn to run against *any* unfamiliar Oracle system:

What is slow? → Who/what is affected? → When did it become slow? → What resource is being consumed? → Where is the workload spending time? → Which SQL/session/process/object/resource is responsible? → What evidence proves the root cause? → What is the safest corrective action? → Did the change actually improve performance?

The course explicitly teaches students to *distrust* the anti-patterns listed in the source brief (bumping SGA/PGA because "it's slow," blind indexing, blind parallelism, killing sessions without diagnosis, reading only Top SQL, reading only wait events, reading only CPU, applying advisor recommendations without understanding them). Every day's Q&A includes at least one "what would you do first?" question specifically to drill the discipline of measuring before acting.

### Learning progression
**Revised per your request to build a proper architecture foundation before performance topics, and to open with something that hooks students rather than a generic welcome.** The course is now **34 days**, organized into 16 progressive stages. It still opens with demonstration before lecture, but Days 3–6 now insert a dedicated Oracle Architecture bootcamp — pure architecture, no performance framing yet — before Stage 1 begins to build performance vocabulary on top of it:

1. Day 1 — The Welcome & Hook (instructor introduction + course roadmap, wrapped around one genuinely striking live demo — not a slide-only orientation)
2. Day 2 — Systematic Investigation: From Symptom to SQL (demonstration-driven, completes the two-session orientation)
3. Days 3–6 — **Stage 0: Oracle Architecture Bootcamp (NEW)** — instance vs. database, memory/process architecture, storage structures, redo/undo, and how a statement actually executes end-to-end — taught with zero performance-tuning framing so it stands on its own as real architecture knowledge
4. Days 7–9 — Stage 1: Foundations (terminology, time model, instrumentation) — now building directly on the architecture just taught
5. Days 10–11 — Stage 2: Performance Diagnostics (V$ views, wait events, OS metrics)
6. Days 12–16 — Stage 3: AWR / ASH / ADDM (the heaviest stage — the daily-use evidence toolkit)
7. Days 17–18 — Stage 4: Wait Events & Bottleneck Analysis
8. Days 19–20 — Stage 5: SQL Performance
9. Days 21–22 — Stage 6: Execution Plans
10. Day 23 — Stage 7: Indexing & Data Access
11. Days 24–25 — Stage 8: Optimizer & Statistics
12. Days 26–27 — Stage 9: Advanced SQL Tuning
13. Days 28–29 — Stage 10: Memory Performance
14. Day 30 — Stage 11: I/O Performance
15. Day 31 — Stage 12: Concurrency & Contention
16. Day 32 — **Stage 12b: RAC & Grid Infrastructure Awareness (NEW)** — a single conceptual day connecting the architecture bootcamp to a clustered environment, anchored by the `rac-status.sh` tool
17. Day 33 — Stage 13: Advanced/Systematic Troubleshooting, including a "which tool answers which question" toolkit-decision lesson
18. Day 34 — Stage 14 / Capstone: full production-incident simulation

**Design note on Stage 14 (unchanged in substance, renumbered):** the source brief lists roughly 15 example production incidents and separately requires "at least 10 complete end-to-end production incident simulations" plus a 20+ scenario library. Fitting 15 dedicated full-incident *days* on top of 16 conceptual stages still does not fit inside a realistic daily pace. Incident-style thinking is threaded through every day's Part C from Day 1 onward; Days 33–34 dedicate themselves to full multi-symptom, multi-hypothesis investigations combining several stages at once; and the required volume — at least 10 fully worked end-to-end incidents, 20+ scenarios overall — lives in **Deliverable 6 (Scenario Library)** and **Deliverable 5 (Lab Catalog)**, referenced from the relevant days rather than each requiring its own calendar day.

**Design note on the RAC day:** you specifically pointed at Fred Denis's `rac-status.sh`, so Day 32 gives RAC/Grid Infrastructure a real, honest single day — enough to make a single-instance-trained DBA dangerous-in-a-good-way when they first sit in front of a cluster (instance vs. cluster resource model, `GV$` views, `rac-status.sh` walkthrough, a conceptual introduction to global cache waits) — without pretending to be a full RAC internals course. Deep RAC/Exadata material stays out of scope here; that ground is already covered by the separate Exadata DBA mentor program.

### Practical / theory ratio
Target 30–40% theory, 30–40% live instructor demonstration, 20–30% guided or independent student hands-on work, averaged across the course (some early foundation days lean slightly more theoretical to establish vocabulary; most days from Day 9 onward lean toward demonstration and lab). Every day still follows the mandated four-part structure (Theory ~15–25 min, Demo ~20–30 min, Scenario ~10 min, Q&A ~5 min).

### Scenario methodology
Every practical demonstration and every scenario follows the same evidence-first pattern: *"Here is the evidence. What hypothesis can we form? How can we prove or disprove it?"* Scenarios always include the symptom, the initial evidence, at least one false lead investigated and ruled out, the proven root cause, the fix applied, and a quantified before/after validation. This mirrors the Tanel-Poder-inspired investigative style identified in the research above, expressed as original course content.

### Tool strategy
Every tool used in the course is labeled by source category the first time it appears:
- **Oracle-provided** — `V$`/`GV$` views, `DBMS_XPLAN`, AWR/ADDM/ASH (Diagnostics/Tuning Pack — see license notes in the Lab Environment section below), SQL Trace/TKPROF, SQL Monitor, `DBMS_STATS`, `DBMS_SQLTUNE`, SQL Tuning Sets, SQL Plan Management, OSWatcher/ExaWatcher and ORAchk/EXAchk (free, part of the Autonomous Health Framework).
- **Public/open-source, third-party** — `tpt-oracle` (Apache 2.0, Tanel Poder), `cscripts` (public GitHub, Carlos Sierra), `eDB360`/`SQLd360` (public GitHub, Sierra/Hoogland/Arao/Poder et al.), OraPub's BloodHound Toolkit and ASH Visualization Tool (free membership download), and `rac-status.sh` (public GitHub, Fred Denis) — see **Deliverable 1B — Performance Engineering Toolkit Map** above for exactly what each one answers and which day it anchors. Every one is cited with its source URL and author, paired with the standard-Oracle-view equivalent so the course never depends on any single external toolset, and none of the reference material's paid/proprietary content is reproduced.
- **Reference-only, not redistributed** — Karl Arao's AWR Tableau Toolkit (the archive you supplied): credited by name, its technique explained, and an original PERF_LAB-scoped adaptation built for Day 14, because no open-source license could be confirmed for the original scripts (see the caution in Deliverable 1B).
- **Original course-created scripts** — the `PERF_LAB` schema, data generators, problem-injection scripts, diagnose/fix/validate/cleanup scripts, and the Day 14 AWR-to-CSV-to-Power-BI/Tableau mini-pipeline, all written for this course.
No proprietary or paid third-party course content is reproduced anywhere in this program.

### Assessment strategy
Daily knowledge checks (3–5 questions: at least one troubleshooting question, one "what would you do first?" question, one scenario-based question — never purely definitional), weekly quizzes at the end of each stage cluster, standalone SQL-tuning and execution-plan interpretation exercises, AWR/ASH interpretation exercises using provided report excerpts, and a small number of full production-incident simulations building up to the Day 30 capstone, which is delivered in both a Student Version (symptoms only) and an Instructor Solution Version (full evidence chain and answer key). Reasoning is graded, not recall — every assessment question requires the student to justify *why*, not just name the correct feature.

### Day 1 & Day 2 — Detailed Design (Hook & Instructor Introduction)

You asked specifically that the opening not feel "like other general" courses — here is the actual design, not just a roadmap row:

**Day 1 structure (60 minutes):**
1. **Instructor introduction (≈5 min).** A short, personal placeholder for you to fill in — name, years as an Oracle DBA, the kind of production incidents you've actually solved, why you built this course this way (evidence-first, not slide-first). Kept deliberately brief so it doesn't eat into the demo.
2. **Course roadmap in one screen (≈5 min).** Not a 34-row table — a single diagram showing the six-stage shape of the journey (Hook → Architecture → Diagnostics → Evidence Toolkit (AWR/ASH) → SQL/Plans/Optimizer → Memory/I/O/Concurrency → Capstone) so students see where they're going before anything else.
3. **The Hook (≈35 min): "The 45-Minute Mystery."** A batch reconciliation job that normally finishes in 4 minutes took 45 minutes this morning, and finance is asking why the daily numbers were late. Instead of reading `V$SESSION` as a wall of text, the instructor opens OraPub's free ASH Visualization Tool (or an equivalent instructor-built chart in the same spirit) and shows the workload's shape over time as a picture — a clean green (CPU) band for the first four minutes of every prior run, and a wide red (wait event) band stretching for forty minutes on today's run. The class watches the investigation go from "picture shows something changed" to "exact SQL_ID and exact wait event" to "here's the row in the plan that changed" in real time. This is the moment that proves the course's core claim: performance engineering is a repeatable investigation, not folklore, and modern tooling makes the evidence visible immediately rather than after an hour of squinting at text.
4. **Q&A (≈5 min).** Not a knowledge check yet — a "what did you notice?" discussion to make sure everyone is oriented and curious for Day 2.
5. **What's different from a generic course intro:** no vendor history, no certification roadmap, no feature-tour slide deck — the entire session is built around proving, in the first hour, that this course will teach a skill the student can use on Monday morning.

**Day 2** keeps the original demonstration-driven design from Phase 1 (systematic investigation from symptom to SQL), now explicitly positioned as "yesterday you watched it happen — today you drive," and closes the two-session orientation before the Architecture Bootcamp begins on Day 3.

## Standard Lab Environment & Package Design

This section defines the reusable lab environment referenced by every day above and by the Lab Catalog (Deliverable 5) that follows in the next phase.

### Database requirements

- **Oracle version:** 19c Enterprise Edition as the primary baseline (matches the research baseline above). Where a demo depends on a 21c/23ai-only feature it will be explicitly marked `21c+` or `23ai+` in that day's lab — nothing 19c-only is presented as universal Oracle behavior.
- **Architecture:** Single-instance, multitenant (one PDB, e.g. `PERFPDB`, inside a CDB) is the default target; every script is written to run identically against a non-CDB instance with a one-line note where a `CDB$ROOT`/`CON_ID` distinction matters.
- **Platform:** Linux x86-64 preferred for OS-level correlation demos (Days 8, 27); the pure-SQL demos work on any platform Oracle 19c supports.
- **Privileges required:** a lab superuser account (e.g. `SYSTEM` or a DBA-granted account) for setup/data generation and for querying `DBA_HIST_*`/`GV$`/`V$` views, plus the `PERF_LAB` application schema itself for day-to-day demo execution. `SELECT ANY DICTIONARY` or the specific `V_$...`/`DBA_HIST_...` grants are listed per script where the default DBA role is not assumed.
- **LICENSE DEPENDENCY:** AWR, ADDM, ASH (including `DBA_HIST_ACTIVE_SESS_HISTORY`), SQL Monitor (Enterprise Manager GUI), and SQL Tuning Advisor/SQL Access Advisor all require the **Diagnostics Pack** and/or **Tuning Pack** licenses on Enterprise Edition. Oracle Database Free / XE and Standard Edition 2 do not include these packs. Every day that uses AWR/ASH/ADDM/SQL Monitor is marked `LICENSE DEPENDENCY` in its lab prerequisites, and — per the source requirement — an alternative is provided: `V$ACTIVE_SESSION_HISTORY` (in-memory ASH) is usable without the Diagnostics Pack on a strict reading of most environments' base V$ access but organizations should verify their own license position before relying on it; Statspack (free, included with every edition) is offered as the AWR substitute for snapshot/report-style analysis; and manual point-in-time sampling of `V$SESSION`/`V$SQL` (in the style of the public `snapper.sql` script referenced on Day 12) is offered as the ASH substitute. This course never assumes a licensed option is present without saying so.

### Standard lab schema — `PERF_LAB`

A single reusable schema representing a realistic order-processing/payments application, sized for the **Standard tier** (4–8 CPU VM, 16–32 GB RAM) selected for this course:

| Table | Represents | Approx. Standard-tier rows | Notes |
|---|---|---|---|
| `CUSTOMERS` | Customer master data | 500,000 | Skewed `REGION`/`STATUS` columns for histogram demos (Day 24) |
| `PRODUCTS` | Product catalog | 50,000 | Function-based-index candidate column (Day 23) |
| `ORDERS` | Order headers | 5,000,000 | Range-partitioned by `ORDER_DATE` (Day 27 partition pruning) |
| `ORDER_ITEMS` | Order line items | 20,000,000 | Primary join-method/index demo table (Days 22–23) |
| `PAYMENTS` | Payment transactions | 5,000,000 | Hot-block/contention demo target (Day 31) |
| `TRANSACTIONS` | General ledger-style transaction log | 10,000,000 | High-volume I/O and TEMP-spill demo source (Days 29–30); also the source table for the Day 14 AWR-to-Power-BI/Tableau history extract |
| `EMPLOYEES` | Internal staff | 10,000 | Small table for baseline/control comparisons |
| `DEPARTMENTS` | Org structure | 200 | Small dimension table |
| `SALES` | Aggregated sales facts | 10,000,000 | Range-partitioned, used for partition-wise join demos (Day 27) |
| `LOG_EVENTS` | Application/event log | 20,000,000 | Insert-heavy table for concurrency/hot-block and redo/log-sync demos (Days 17, 31) |

A **Small tier** (laptop/VM, Oracle Free/XE) row-count profile at roughly 5–10% of the above, and a **Large tier** profile at 3–5x the above, will be published alongside the Standard-tier generator when the setup scripts are built (Phase 2), so instructors can scale the same schema to their hardware without changing any demo SQL.

**RAC Lab (optional, Day 32 only):** the Standard/Small/Large tiers above are all single-instance by design — that's sufficient for every day except Day 32. Day 32 is explicitly marked `ENVIRONMENT DEPENDENT`: if a 2-node RAC lab is available (e.g. a local VM cluster or a cloud trial), `rac-status.sh` and `GV$` cross-instance queries run live; if not, the day still delivers full value using a captured sample `rac-status.sh` output and worked `GV$` query results, with the conceptual/architecture content (which doesn't require a live cluster) carrying the rest of the session. No student is required to stand up a personal RAC environment for this course.

**Day 14 toolkit adaptation note:** rather than running Karl Arao's original multi-node SSH orchestration (built for consolidated Exadata estates), Day 14's lab is a single-instance version of the same idea against `PERF_LAB`: extract several simulated days of AWR history for `TRANSACTIONS`-heavy workload snapshots into the same kind of AAS-based CSV his `awr_topevents`/`awr_cpuwl` scripts produce, then load that CSV straight into Power BI or Tableau (skipping his `AWR_*` warehouse/staging-table layer, which exists to merge many clients' histories and isn't needed for one training lab). This keeps the technique — and the credit — intact without redistributing his original scripts (see the IP caution in Deliverable 1B).
