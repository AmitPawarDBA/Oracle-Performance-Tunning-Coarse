# Day 4 — Architecture Bootcamp II: Storage — Datafiles, Tablespaces, Segments, Redo & Undo

## Topic
Physical and logical storage architecture in Oracle Database 19c: how a row of data is actually stored on disk (datafiles → tablespaces → segments → extents → blocks), and the two mechanisms that make every write durable and every read consistent — the online redo log and the undo (rollback) mechanism. This is the second of four Architecture Bootcamp sessions (Days 3–6) and is taught with **zero performance-tuning framing** — it stands on its own as core Oracle architecture knowledge every DBA needs regardless of whether they ever touch a tuning problem.

## Duration
60 minutes (Theory ~20 min, Demo ~25 min, Scenario ~10 min, Q&A ~5 min)

## Difficulty
Beginner

## Learning Objectives
By the end of this session, students will be able to:
1. Explain the physical-to-logical storage hierarchy in both directions — bottom-up (block → extent → segment → tablespace → datafile) and top-down (datafile → tablespace → segment → extent → block) — and correctly place any Oracle storage term into that hierarchy.
2. Decode a ROWID into its component parts (data object number, relative file number, block number, row number) using `DBMS_ROWID`, and trace it through `DBA_EXTENTS`/`DBA_DATA_FILES` to a physical file on disk.
3. Explain why online redo logs exist (durability/crash recovery) and describe the lifecycle of a redo log group through `CURRENT` → `ACTIVE` → `INACTIVE`.
4. Explain why undo exists — both for transaction rollback AND for read consistency — and correctly refute the two most common beginner misconceptions about it.
5. Read `V$TRANSACTION`, `V$MYSTAT`/`V$SESSTAT`, and `V$UNDOSTAT` well enough to observe redo and undo being generated by a live transaction.

## Theory

Every table you have ever queried is, underneath Oracle's SQL layer, just a carefully organized region of bytes on one or more operating-system files. Understanding that stack — and both directions through it — is the single most useful piece of architecture knowledge for a working DBA, because almost every storage-related question ("why is this tablespace full," "where did this row come from," "can I shrink this file") is really a question about where you are in this hierarchy.

**Bottom-up: block → extent → segment → tablespace → datafile.** The *block* is Oracle's smallest unit of I/O — typically 8KB — and it is where rows physically live, packed together with a small header and free space controlled by `PCTFREE`. Oracle never asks the operating system for one block at a time; it allocates blocks in groups called *extents*, contiguous within a single datafile. A *segment* is the full set of extents belonging to one database object — a table, an index, an LOB, undo, or temporary sort space — and it is the segment, not the individual extent, that has a name you can query (`DBA_SEGMENTS.SEGMENT_NAME`). Every segment lives inside exactly one *tablespace*, which is Oracle's logical umbrella — the thing you assign quota against, back up, and take online/offline as a unit. A tablespace itself has no bytes of its own; it is a name mapped onto one or more physical *datafiles*, which are the actual operating-system files where every byte ultimately resides.

**Top-down: the same hierarchy read the other direction.** Start from a datafile and you find it belongs to one tablespace. That tablespace contains many segments, spread arbitrarily across however many datafiles the tablespace has. Each segment is made of one or more extents, and each extent is a contiguous run of blocks inside one specific datafile. This is why `DBA_EXTENTS.FILE_ID` and `DBA_EXTENTS.BLOCK_ID` together, not the tablespace name, are what pin a piece of data to a physical location — the tablespace is an administrative grouping, not itself a storage location. Teaching this both directions matters: students who only learn bottom-up can trace a row to a file but cannot reason about capacity planning; students who only learn top-down understand space allocation but cannot answer "where does *this* row live."

**Redo: why it exists.** Oracle buffers changed blocks in memory (the buffer cache) and does **not** write them to disk synchronously on every change — that would be far too slow. Instead, every change generates a *redo change vector* — a compact record of "what changed" — which the log writer process (LGWR) flushes to the *online redo log* at commit time (and at several other trigger points). This is the durability guarantee: if the instance crashes one second after your commit, the committed data block itself may still only exist in memory, but the redo describing that change is already safely on disk, and instance recovery replays it. Redo logs are organized into numbered *groups*, each with one or more identical *members* (mirrored copies for safety), and LGWR writes to whichever group is currently `CURRENT`. When that group fills, Oracle performs a *log switch* to the next group; the just-vacated group becomes `ACTIVE` until every change in it has also been permanently checkpointed to the datafiles, then `INACTIVE` once it's safe to reuse (and, in `ARCHIVELOG` mode, once it has been archived).

**Undo: why it exists — and the two jobs it does.** Undo exists to make every DML statement reversible. Before Oracle changes a block, it first writes the block's *pre-change image* into an undo segment. This is what makes `ROLLBACK` possible — and it's also what makes every failed statement automatically and completely reversible without any application code. That is job one, and it's the one most beginners learn first, which is precisely why it becomes a trap: **"undo is just for rollback" is a genuine misconception.** Undo's second job — arguably the more important one in a busy production system — is **read consistency**. When your query starts, Oracle notes the current System Change Number (SCN) as the query's snapshot point. If, while your query is still running, another session changes and commits a block your query hasn't reached yet, your query does not see that new value — Oracle detects the block has changed since your snapshot SCN, locates the relevant undo, and reconstructs the block exactly as it looked at your query's start time. Every single query you run gets this guarantee automatically, whether or not any rollback ever happens anywhere. This is also why a long-running report can fail with `ORA-01555 snapshot too old` — the undo it needs to reconstruct an old block may have already been overwritten by newer transactions if `UNDO_RETENTION` and undo tablespace sizing weren't generous enough for that query's runtime.

**A second common misconception worth killing early: "redo and undo are the same thing."** They protect against different failures and travel in different directions. Redo is *forward-looking*: "if I crash, replay this change so it isn't lost." Undo is *backward-looking*: "if I need to reverse this change, or reconstruct an earlier version, here's what it looked like before." The two are also linked in a way students find genuinely surprising: **writing undo itself generates redo.** Undo blocks are ordinary database blocks living in the UNDO tablespace, and like any other block change, changing them is protected by a redo change vector — so a single row INSERT generates both an undo change vector (in case it needs to be rolled back or read-consistently reconstructed) and a redo change vector protecting *that* undo write, on top of the redo change vector protecting the original data block change. Seeing this live in `V$MYSTAT` — 'redo size' and 'undo change vector size' both climbing from the exact same INSERT statement — is the moment this stops being an abstract diagram and becomes something students actually believe.

## Key Concepts

- **Data block** — smallest unit of Oracle I/O (commonly 8KB); holds row data plus a header, row directory, and free space.
- **Extent** — a contiguous set of blocks, in one datafile, allocated to one segment at a time.
- **Segment** — the complete set of extents for one object (table, index, undo segment, temp segment, etc.); has one name, one owner, one type.
- **Tablespace** — a logical, named storage container mapped onto one or more datafiles; the unit of quota, backup, and online/offline administration.
- **Datafile** — the actual operating-system file holding the bytes; belongs to exactly one tablespace.
- **ROWID** — a physical address encoding data object number, relative file number, block number, and row number within the block.
- **Online redo log** — a set of log groups LGWR writes to, protecting every committed (and some uncommitted) change against instance failure.
- **Log switch** — the move from a full CURRENT group to the next group, cycling through ACTIVE and INACTIVE states.
- **Undo segment** — where the pre-change image of a block is stored, enabling rollback and read consistency.
- **Read consistency** — the guarantee that a query sees data as of the moment it started, regardless of concurrent commits by other sessions.
- **UNDO_RETENTION** — how long Oracle *tries* to retain committed undo before it becomes eligible for reuse; not a hard guarantee under space pressure.

## Important Views / Commands

| View / Package | Purpose |
|---|---|
| `DBA_TABLESPACES` | Inventory of tablespaces, type, extent/segment management mode |
| `DBA_DATA_FILES` | Physical datafiles: file name, size, tablespace, autoextend status |
| `DBA_SEGMENTS` | Segments (table/index/undo/etc.), size, extent count, tablespace |
| `DBA_EXTENTS` | Every extent: which segment, which file, which starting block, how many blocks |
| `DBA_FREE_SPACE` | Free (unallocated) space chunks per tablespace |
| `DBMS_ROWID` package | `ROWID_OBJECT`, `ROWID_RELATIVE_FNO`, `ROWID_TO_ABSOLUTE_FNO`, `ROWID_BLOCK_NUMBER`, `ROWID_ROW_NUMBER` — decode a ROWID into its parts |
| `V$TRANSACTION` | Active transactions: undo segment used, undo blocks/records consumed, start time |
| `V$ROLLSTAT` / `V$UNDOSTAT` | Undo segment statistics; `V$UNDOSTAT` is a 10-minute-bucketed instance-wide undo activity history |
| `DBA_ROLLBACK_SEGS` | Undo segment names and their owning tablespace |
| `V$LOG` | Redo log groups: status (CURRENT/ACTIVE/INACTIVE), size, sequence# |
| `V$LOGFILE` | Physical member files behind each redo log group |
| `V$THREAD` | Redo thread status (one thread per instance; matters more once RAC is introduced on Day 32) |
| `V$MYSTAT` / `V$SESSTAT` + `V$STATNAME` | Session-level statistics, including `redo size` and `undo change vector size` |
| `AS OF TIMESTAMP` / `AS OF SCN` (flashback query) | Read a past, undo-reconstructed version of a row without any rollback |

## Practical Demo

*(Baseline/orient → trace → observe → verify → reset, adapted for a conceptual architecture day rather than an incident. Full SQL for every step is in `demo.sql`.)*

1. **Orient.** Look at `DBA_TABLESPACES` and `DBA_DATA_FILES` for the whole instance first, so students see the full hierarchy exists before zooming into one table (`diagnose.sql` D1–D2).
2. **Baseline the demo table.** Query `D4_DEMO_ORDERS` (created in `setup.sql`, a small dedicated table so the trace stays to one extent) and pull one row's `ROWID` directly in a `SELECT`.
3. **Decode the ROWID.** Run `DBMS_ROWID.ROWID_OBJECT`, `ROWID_RELATIVE_FNO`, `ROWID_TO_ABSOLUTE_FNO`, `ROWID_BLOCK_NUMBER`, and `ROWID_ROW_NUMBER` against that same ROWID and read each piece aloud against the theory diagram.
4. **Confirm bottom-up.** Join the decoded absolute file number and block number against `DBA_EXTENTS` to find the one extent that owns that block, then against `DBA_DATA_FILES` to name the actual OS file.
5. **Confirm top-down.** Independently query `DBA_SEGMENTS` for the same table (extents, size) and `DBA_EXTENTS` ordered by `extent_id`, and show the extent count agrees both ways — bottom-up and top-down meet in the middle.
6. **Generate and observe redo.** Snapshot `V$MYSTAT` for `'redo size'`/`'redo entries'`/`'user commits'`, run a 5,000-row insert into the scratch table `D4_REDO_DEMO`, commit, and snapshot again — students watch the numbers move in real time (**ENVIRONMENT DEPENDENT**: exact byte deltas vary by hardware/load).
7. **Generate and observe undo, then prove read consistency.** Before committing a second insert, query `V$TRANSACTION` to show `USED_UBLK`/`USED_UREC` climbing on an *uncommitted* change; after committing, show the transaction row disappears from `V$TRANSACTION` while the undo data itself persists — then (ideally with a second session open) run the Part C read-consistency demonstration where a slow-running query keeps returning its snapshot's original value even after another session commits a change to the same row.
8. **Verify understanding and reset.** Run `validate.sql`'s PASS/FAIL checks live to confirm the class's mental model matches Oracle's actual behavior, then run `reset.sql` so the demo table is pristine for the next section/group.

## Real-World Scenario

**"Where does my data actually live, and what happens the instant I commit?"**

A colleague who's strong in SQL but new to Oracle internals stops by your desk: *"I inserted a row into ORDERS and hit commit. What actually just happened, physically, on the server?"* This is not an incident — it's a walkthrough you build together, step by step, using real queries.

**Step 1 — "Where is the table itself?"** You run `DBA_SEGMENTS` for `PERF_LAB.ORDERS` and show it isn't one file — it's range-partitioned by `ORDER_DATE`, so it's actually many segments (one per partition), each with its own extents, possibly spread across several datafiles in the `PERF_LAB_DATA` tablespace. You explain this is exactly why the clean row-trace demo today used a small dedicated table instead — with 5 million rows across dozens of extents and partitions, the same trace is still *true*, just noisier to look at on Day 4.

**Step 2 — "OK, so what happens when I INSERT?"** You walk through it in order: Oracle finds (or allocates) a block in the correct partition's segment with enough free space; before changing that block, it first writes the block's undo — in this case there's no "before" row yet, so the undo records "this row didn't exist," which is exactly what makes `ROLLBACK` able to make it disappear again if you don't commit. The block, now containing your new row, is changed **in the buffer cache** — not yet on disk. Simultaneously, a redo change vector describing both the data-block change and the undo-block change is written to the **log buffer**, in memory.

**Step 3 — "So when does it actually hit disk?"** This is the part people usually get backwards. At `COMMIT`, Oracle does **not** force the changed data block itself to disk. What it forces, synchronously, is the **redo** — LGWR flushes the log buffer's contents (including this transaction's change vectors) to the online redo log member(s) on disk, and only once that write is confirmed does the commit return "success" to the session. The changed data block sits safely in the buffer cache and gets written to its datafile later, in its own time, by DBWn (database writer) — driven by checkpoints, cache pressure, or a few other triggers, not by every individual commit. This is what makes Oracle fast: one small sequential write to redo per commit, versus a potentially large random write per commit if data blocks had to be flushed immediately.

**Step 4 — "So if the server crashes right after my commit, is my data safe?"** Yes — and this is the payoff of the whole walkthrough. Because the redo was durably written before commit returned, instance recovery on restart replays that redo against the datafiles, reconstructing your committed change even though the data block itself was never flushed before the crash. Durability comes from redo, not from the data block reaching disk immediately.

**Step 5 — "And if I'd made a mistake and rolled back instead?"** You point back to the undo written in Step 2: an uncommitted transaction reverses itself by applying its own undo records back onto the changed blocks, restoring them to their pre-transaction state — cheap, fast, and entirely separate from the redo mechanism that just protected the commit.

**Lesson:** one row, one commit, and underneath it: a block change, an undo write, a redo write, a synchronous log flush, and an asynchronous data-file write — four Oracle background/foreground actors (the session's server process, LGWR, DBWn, and later SMON/checkpoint activity) cooperating to give you both durability and reversibility, without you ever having to think about it.

## Troubleshooting Challenge

**Symptom:** A teammate reports that the `PERF_D4_REDO_TS` tablespace (or, in a real system, any application tablespace) is "unexpectedly running low on free space," and asks you to figure out why before simply extending the datafile.

**Work through it using `diagnose.sql`:**
1. Run the used/free/percent-full query (`diagnose.sql` D5) to confirm the symptom and get an exact `pct_used` number rather than trusting a vague "it's almost full."
2. Run D6 to rank segments in that tablespace by size — is one segment unusually large, or is space spread evenly across many objects (pointing at organic growth vs. one runaway table)?
3. Run D7 to look at that segment's extent map — lots of small extents can indicate `AUTOALLOCATE` fragmentation; a few huge extents suggest bulk-load growth.
4. Run D8 to compare `DBA_SEGMENTS`-allocated size against the table's actual row count/blocks from `DBA_TABLES` — a segment that's much bigger than its current row count justifies is a classic sign of heavy deletes that never released space back to the tablespace (segment high-water mark stayed put even though most rows are gone).
5. Decide: does this need more datafile space (real growth), or does it need `ALTER TABLE ... SHRINK SPACE` / a rebuild (bloat from deletes)? **Do not immediately add a datafile as a reflex fix** — that's exactly the kind of "add resources without diagnosing" habit this course trains students away from, even on a pure architecture day.
6. State your conclusion in one sentence with the evidence that supports it (this format — evidence first, conclusion second — is the same discipline used in every scenario for the rest of the course).

## Q&A

1. **(Troubleshooting)** A student ran `DBA_EXTENTS` for a table and got back 40 rows, but `DBA_SEGMENTS.EXTENTS` for the same table says 38. What are the two most likely explanations, and how would you check which one it is? *(Answer key: stale/cached dictionary view join issue is unlikely since both are live dictionary views off the same underlying data — more likely the student filtered `DBA_EXTENTS` incorrectly, e.g. missed a `WHERE OWNER=...` and picked up a same-named segment from another schema, or the table has an index/LOB segment being confused with the table segment. Re-run with explicit `OWNER` and `SEGMENT_TYPE` filters.)*
2. **(What would you check first?)** Someone says "our database lost data after a crash." What's the very first thing you check, and why does that check matter more than looking at the data files themselves? *(Answer key: check whether instance recovery ran cleanly and what redo it applied — `ALERT LOG` and `V$RECOVERY_LOG` / recovery messages at startup — because redo, not the datafile state at the moment of the crash, determines what should have survived.)*
3. **(Scenario-based)** A long-running report fails partway through with `ORA-01555: snapshot too old`, but the report itself never modifies any data. Why would a read-only query ever be affected by undo? *(Answer key: read consistency depends on undo staying available for the whole duration of the query; if other sessions generate enough new undo to overwrite what this query still needs — because `UNDO_RETENTION`/undo tablespace sizing couldn't hold it that long — the query can no longer reconstruct its snapshot and fails.)*
4. **(Mixed/definitional-but-applied)** Why does an `INSERT` generate both undo and redo, when undo already generates its own redo to protect itself? Isn't that redundant? *(Answer key: no — they protect against different failures. Redo protects the whole set of changes, including the undo block's own change, against instance crash/media loss. Undo protects the ability to reverse or read-consistently reconstruct the data change. Losing either one loses a different guarantee.)*

## Student Notes

- The hierarchy, memorized both directions, is worth more than any single command in this lesson: **block → extent → segment → tablespace → datafile**, and back.
- A `ROWID` is not an opaque ID — it is literally an address. `DBMS_ROWID` is how you read that address.
- Undo has two jobs: rollback (reversing your own uncommitted changes) and read consistency (letting every query, including other people's, see a stable snapshot). Read consistency is the one people forget.
- Redo protects durability (nothing committed is ever lost, even on a crash). Undo protects reversibility and consistency. They are related — undo writes generate redo too — but they solve different problems.
- `COMMIT` forces redo to disk synchronously; it does **not** force the changed data block to disk synchronously. That asymmetry is why Oracle commits are fast.
- Keep your `demo.sql` output from today — the file/block/extent numbers you traced are a good self-quiz next week: re-derive them from scratch without looking.
